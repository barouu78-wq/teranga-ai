# Recevoir une relecture

Adapté de Superpowers (`receiving-code-review`), licence MIT : voir `.claude/skills/LICENCE-superpowers.txt`.

**Règle : vérifier avant d'appliquer.** Une remarque est une piste, pas un ordre. Les demandes du propriétaire
sont l'exception : elles se suivent, après les avoir comprises.

## Pour chaque remarque
1. **Lire toute la relecture avant d'agir.** Si un point est flou, poser la question avant de toucher aux autres :
   les points peuvent être liés.
2. **Reformuler ce qui est demandé.**
3. **Vérifier dans le code** que le problème décrit existe vraiment : le reproduire par un test ou une mesure, comme
   pour un bug (skill `deboguer-methodiquement`).
4. **La remarque est juste** : corriger, avec un test qui échoue avant la correction. Traiter une remarque à la fois
   et tester chacune.
5. **La remarque est fausse ou démesurée** : répondre avec la raison technique, c'est-à-dire ce qui a été vérifié
   et le test qui le montre. Pas de « vous avez raison ! » ni de remerciement de politesse : dire ce qui a été
   corrigé, et où.
6. **La remarque contredit une décision du propriétaire, ou demande une grosse refonte** : lui poser la question.

## Ordre de traitement
1. Ce qui bloque et la sécurité.
2. Les petites corrections.
3. Le reste.

Ne jamais affaiblir le CSRF, les limites, la CSP ni les hôtes de confiance pour faire taire une remarque.

## Répondre
- **Sur GitHub** : répondre dans le fil du commentaire, en français, en terminant par le pied « Generated by
  Claude Code », et dire quel commit corrige.
- **Bot qui ne relit pas** (quota Codex épuisé, par exemple) : il n'y a rien à corriger, le noter simplement.
- **Fonction à « faire proprement » suggérée** : vérifier qu'elle sert vraiment (`grep`) avant de l'écrire.
